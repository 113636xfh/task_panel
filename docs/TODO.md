## 1. 验收（Judge）是否另开会话 — 待讨论

- **提出**：2026-07-21，P2 验收后用户质疑「验收与执行同会话」的独立性
- **现状**：一任务一 pi 会话全程不换；验收是同会话内的独立评审回合（prompt 要求扮演独立验收官，逐项判定写 `work/review.json`；标准优先用户原始 `acceptance_text` > `plan.acceptance`；≤3 次重试后转人工确认）
- **现行设计的理由**（详见当日讨论记录）：
  1. 判据完整：judge 持有全过程（分支决定、阻塞决策、执行动机、test 原始输出），能判"方向"不只"产物"——**最强一条**
  2. 零传递成本：无"执行者写汇报、judge 读汇报"失真
  3. 成本/延迟：同会话命中最长前缀缓存；另开 = judge 冷启动重读工作区，本地 27B 下验收是最敏感等待点
  4. 重试回路简单：执行者记得上轮哪条被判 fail，定向修
  5. 工程简单：一任务一进程一 checkpoint
  6. prompt 级"独立"缓解——**最弱一条，即质疑点**：27B 级模型角色隔离弱，主观"质量/符合度"项存在自我宽恕风险
- **改另开的核心论据**：判据可以注入，"角色独立性"注入不进去（LLM-as-judge 主流推荐独立 judge；Devin/Cursor reviewer 亦为独立 agent）
- **要拍板的点**：
  1. **judge 输入边界**：只给「任务描述 + 验收标准 + 产物清单」让它自己读工作区（最独立、最贵）vs 附带执行者变更摘要（折中）？
  2. **反馈回路**：fail 时 judge 逐条意见如何进执行者下一回合（机制已有，来源从"会话记忆"变"注入 review.json"）
  3. **延迟预算**：judge 冷启动读区 × 最多 3 轮重试，本地模型下可接受吗
  4. **test_cmd 定位**：客观验证本就与会话无关，改后 judge 专注主观项
- **倾向（待用户确认）**：主观验收项值得另开；"判据完整"缺口用注入决策记录摘要补；主要代价是延迟 + token
- **状态**：⏸ 待用户实际使用一段时间后再决定
